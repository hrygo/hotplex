Task Q1: RULING — 'queued' is a RUNTIME fact, not a new delivery status. Delivery stays accepted; only runtime_status becomes queued. A queued row holds NO owner lease and NO worker_run_id: it has not crossed the dispatch boundary, so holding a lease would let lease recovery fence an input nobody ever sent. Task Q1: RULING — the plan proposed enforcing the global limit with a conditional increment on a shared budget row, paired with decrements on every delete path. THE DECREMENT IS THE DESIGN FLAW, and the migration test caught it: SQLite does not fire row triggers for every row an ON DELETE CASCADE removes (two queue rows, one trigger firing), and a decrement in application code would be skipped by whichever future path forgets it. A leaked slot is a queue that silently refuses everything forever. Changed to: the budget row is WRITTEN first as the cross-instance lock (UPDATE ... SET used = used — a no-op write that still takes the row lock on PG and the write lock on SQLite), capacity is decided from an exact COUNT(*) inside the same transaction, and `used` is refreshed as an observability mirror that is never consulted for the decision. Every delete path — dispatch, cancel, TTL sweep, session delete cascade — is now correct for free and a stale value can never refuse an enqueue. Deviation from the plan's suggested mechanism, same requirement it was expressing (a lock-free COUNT would let two transactions both see room and both insert).
Task Q1: RULING — lock order is fixed at budget row, then per-session counter row. The per-session counter row is bumped BEFORE the per-session COUNT so concurrent enqueues for one session serialise on it and cannot both pass the limit. Reversing the order on any future path is a deadlock, so it is fixed in one place.
Task Q1: RULING — FIFO order is a DB-assigned ordinal (execution_queue_counters.next_seq), never a client clock. Two gateways cannot disagree about who is next, and UNIQUE(session_id, queue_seq) makes the allocator's correctness a DB-enforced fact rather than a convention.
Task Q1: RULING — capacity refusal never evicts. ErrQueueFull refuses the NEW input; the queue holds only inputs that were already acknowledged. Dropping an accepted input to make room would turn a durable promise into a silent loss.
Task Q1: RULING — input idempotency is checked FIRST inside the transaction, so a retry consumes neither an ordinal nor a budget slot.
